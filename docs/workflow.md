# 当前 BD 工作流（workflow）

本文件说明从“用户给定存档和主技能”到“数值 + 网页”的通用流程，以及新机制接入与最小语义验证的规则。操作入口是仓库根 [README.md](../README.md) 与 [AGENTS.md](../AGENTS.md)；字段细节见 [docs/contracts/](contracts/)。

## 网页验证的默认最小范围

- 只导入存档、更新数值或复用现有页面模板：确认本次 HTML 已生成、链接指向当前案例即可；默认不打开浏览器，也不重新操作已验证的控件。
- 修改页面结构或样式：最多打开一次默认页面，确认能够显示且没有明显阻断；不逐页巡查。
- 修改交互或重算服务：只选一条直接相关的操作路径，看到一次成功结果即停止；已有观察足够时不重复核对其它页或同一结果的多个位置。
- 只有用户明确要求完整验证时才运行完整矩阵。完整报告/新增机制知识是功能交付要求，不自动授权完整网页验收。
- 最小验证发现问题时，只修复该阻断并复查同一路径；先交付结果和链接，未做完整验证不作为扣留交付的理由，也不宣称已完成完整验证。

## 日常执行顺序

1. 先冻结、解析用户本次指定的存档，生成独立 BuildSpec 与 calculation-input。只检查当前输入和解码必需依赖；不要运行默认案例 doctor，也不要在导入前完整检查任何其它案例。
2. 导入后按当前构筑的技能、节点、被动、装备、神像、祝福及词条稳定 ID 查询沉淀知识，绑定当前实例的数值和点数。只按命中记录追溯必要证据。
3. 复用统一 DPS 流程的属性、乘区、暴击、目标、时间与报告组件。hit/DoT 仅表示击中与持续伤害的计算组件差异；技能行为由数据和规则表达，不能按技能建立独立 DPS 模型。
4. 优先生成当前 BD 的结果和网页；区分研究/候选产物与可用于当前声明范围的计算结果。机制未知可以显式假设或缩小范围继续；已知来源、执行或账本错误不能用 partial 掩盖。
5. 复用已验证能力且未改变语义时，默认不追加测试阶段；新增/修改语义时按受影响边界做少量正反例，详见下文“新机制接入与最小语义验证”。完整回归须用户单独明确要求。

所有历史案例地位相同，均为以前使用或建立流程留下的实例。案例名不决定默认输入、必读材料、知识检索顺序、回归基线或交付门槛。

## 操作流程

从仓库根目录调用 `scripts/le.ps1`。首次使用先获取 dataset 并自检（见 [README.md](../README.md)）：

```powershell
.\scripts\fetch_dataset.ps1 -Repo BlaCatFishLE/LastEpoch-AIBuildSimulator
.\scripts\le.ps1 doctor
```

然后按当前存档与主技能执行。**完整首接需要用户自备可选的 Node + `lastepochsupertools v1.3.1`**（不随仓库分发；缺依赖时明确 `needs_input`）。没有这些工具时，可做骨架导入或 planner 手工流程，但不会自动得到可计算的 DPS：

```powershell
# 1) 完整首接（当前 V1 仅显式 BH 路线；需要 --tool-home 指向 lastepochsupertools）
.\scripts\le.ps1 import --case examples\<case>\case.json --save '<当前角色存档>' --main-skill bh2 --model black-hole --tool-home '<lastepochsupertools目录>'
# 其它技能：先研究接入（--model research），再在 prepare 指定主技能
.\scripts\le.ps1 import --case examples\<case>\case.json --save '<当前角色存档>' --model research --tool-home '<lastepochsupertools目录>'
# 无外部工具：骨架导入（clean-room；仅 bd.json + 案例骨架）
.\scripts\le.ps1 import --case examples\<case>\case.json --save '<当前角色存档>'

# 2) 准备：冻结输入 → BuildSpec → 计算输入 → 词缀 → 分析产物 → 快照 → 最小校验
.\scripts\le.ps1 prepare --case examples\<case>\case.json --main-skill <ID>

# 3) 计算：仅从冻结输入执行，输出到 reports\<case-id>\<run-id>\
.\scripts\le.ps1 run --case examples\<case>\case.json

# 4) 校验（不重新计算）与打开报告
.\scripts\le.ps1 validate --case examples\<case>\case.json
.\scripts\le.ps1 serve --case examples\<case>\case.json --port 8765
```

- 新案例可用 `examples/_template/` 作为空模板；`import` 会生成或补齐案例骨架。`examples/` 下除 `_template/` 外都是用户本地产物（gitignored），任何案例私有输入放在该案例的 `inputs/` 下，不写进通用规则。
- 没有存档时可用 planner payload（Last Epoch Tools 本地 JSON）路线：`le_build import --file ... --share-id ... --offline` → `le_build export` → 补齐案例字段 → prepare/run（见 `tools/build_import/README.md`）；该路线不依赖 Node，但是进阶手工流程。
- 导入后读取本案例 `onboarding-report.json` 指向的 analysis-plan / coverage / research-queue。已命中共享知识绑定当前值；只补缺失且影响本次结果的规则。
- 重复运行复用已有输入和缓存，不主动无缓存重跑，不在交付前比较多个历史案例。
- 计算和网页使用同一结果数据与同一计算入口；hit/DoT 组件可以有不同数学规则，技能名不能成为选择另一套 DPS 系统的依据。现有技能耦合必须按实现事实登记，不能仅改名宣称统一已完成。
- `package` / `check_package.py` 用于按显式清单生成并校验发布包（可选流程，见 [version-control.md](version-control.md)）。

## 新机制接入与最小语义验证

本节是各入口共同引用的现行流程规则，适用于新技能、新作用主体、新伤害组件、触发/转移/条件/调度能力及旧能力修正；不是回归清单，也不是已实现能力声明。保留先导入当前存档、优先交付、按需研究和最小网页验证的顺序。

### 1. 先区分未知与错误，再决定交付范围

| 情况 | 可以继续做什么 | 交付时的边界 |
|---|---|---|
| 游戏规则/倍率/事件率证据不足，但能给出明确的候选解释 | 用具名假设、有限范围或有依据的参数区间建模；保留推翻假设的证据入口 | 可交付该假设下的结果，不称游戏实测确认；未知不必全部先解决 |
| 所需能力未实现，但可分离出已支持的组件 | 先计算可分离的部分，或实现满足本次需要的最小公共能力 | 写清包含/排除范围；其余留在研究队列，不伪造为 0 或静默套用另一模型 |
| 来源身份错误、必需输入缺失，或字段被忽略/串域/重复计入/账本与数值冲突 | 修复或隔离受影响路径；仍可交付输入、证据、候选网页及未受影响的结果 | 受影响数值不标可用、不替换可用 canonical；partial 不能充当实现错误豁免 |
| 只是全仓回归或游戏内实测未做 | 保留已有适用证据，继续当前任务 | 如实限定已验证范围，不因此要求全量测试或停止其它工作 |

三个维度分别记录：机制证据（沿用 evidence_state）、实现能力（沿用 implementation_state/能力声明）、本次验证（实际 checks 与记录）。本节不增加 schema 状态枚举。coverage 仅描述声明范围内的覆盖；明确假设留在 assumptions/issues，不能因软件通过就删掉。

### 2. 开工只需一段简短的语义说明

复用当前 analysis-plan / 研究队列 / 实施记录，写明本次输出范围、真实来源、使用的公共能力、尚待确认的假设；无需另建大方案或逐词条登记表。新增能力时再补：哪些字段驱动数值，哪些只是身份/展示/推导记录，改动最可能破坏哪条边界。

- 当前存档/目录身份、已分配点数、装备实例是事实；Buff 激活、目标、上游事件率可以是场景。事实查找失败不得用场景默认值冒充成功绑定。
- 需要假设来源时，显式使用场景假设的来源类别和限制，不生成假的 item/node/actor verified 记录。已有来源为零点或可选来源不存在时，按契约不适用/无事件处理；数据缺失、身份冲突则记录缺口或拒绝受影响计算，不能统统捕获异常后补默认。
- 实例/actor 身份、作用域、行为标签与伤害类型/通道分别表达。属性转移要保留原来源、比例、标签和条件；“来源已验证”不等于“作用于所有组件”。跨类型转换、继承或快照确有规则时，显式声明并验证该规则。
- 每个运行期输入只有一个权威。编译期可以折叠纯静态值，但须能追溯推导，派生镜像不得与权威冲突；运行时可变条件/场景不能被冻结后仍作为可操作字段展示。
- 公共能力可增量扩展，只支持已声明的组合即可；暂不支持的组合明确返回缺口/拒绝，不静默计算成另一个组合。

不因普通机制未知反复请求授权。确需用户选择主技能、改变主要伤害口径或决定无法合理界定的关键假设时，再针对该项提问；其余独立工作继续。

### 3. 按变更选择证据，不能把下表当成全跑矩阵

纯输入实例更换或文案/索引修改，沿用既有门禁，不追加下面的检查。新增/改变语义时，通常用一个最小正例和一个能区分错误实现的反例覆盖主要风险；只有独立改变了其它边界，才追加相应检查。一个用例可覆盖多行，已有同实现/同语义边界的有效证据无需重跑。

| 本次改变的边界 | 按需选择的区分性检查 |
|---|---|
| 类型、标签、actor/owner 作用域或继承 | 一条带明确作用域的贡献只影响目标组件；换成不匹配类型/主体后应排除，且不新增 gap；另有明确转换规则时按规则变化 |
| 真实来源绑定、可选来源、来源所有权 | 用当前输入副本移除/置零来源或替换稳定 ID；应失效/不适用/拒绝，不能被默认值补回；同所有权冲突不能多计 |
| effects、聚合、条件、编译期折叠 | 合法修改一个实际数值或条件，检查预期分项/账本变化；镜像冲突应拒绝。改值不必总改变总 DPS（可能钳制、条件关闭或不适用），但原因必须与实际应用记录一致 |
| 频率、生命周期、窗口或控件 | 明确单位、稳态与有限窗口区别；检查一个有效变化与一个相关边界（如零值或未知 policy）。零值支持为空结果还是不支持，应在能力契约/UI/API 一致声明 |
| 新执行分支或结果投影/门禁 | 对相关结果副本做一次有针对性的语义篡改（如虚报 complete、悬空组件、分项与总量冲突），应被实际阶段门禁拒绝；不只测哈希变化 |

检查优先用小型手算 oracle、现有公共 API 和内存副本；不修改冻结存档/目录/历史 run。不要复制实现公式再算一遍当 oracle，也不要把历史 DPS 相等当唯一正确性证据。测试数目、源码不存在技能字符串、JSON Schema 通过均只是局部证据。

新增能力合成检查通过后，在当前真实绑定链接一次结果，核对**受影响的**来源→effect→组件/应用账本→分项/总量；一个当前案例即可，不自动扩成历史组。候选网页可先生成，影响结果可用性的检查在宣称该范围可用前完成；非阻断研究和知识收尾可继续后置。

### 4. 结果门禁和交付用语

- 完整性检查证明产物未变，来源检查证明输入身份，语义门禁证明声明范围内的关系自洽；三者互不替代。
- 组件引用只解析到声明或实际输出单元，不能把待验证账本的引用加入合法集合来自证。合法零贡献/零事件不等于数据缺失。
- coverage 和应用摘要投影自实际应用/未解析记录，不能只检查 status 枚举与 gaps 长度；正常不适用、条件未满足与未解析伤害缺口分开。
- 分项、应用/事件、窗口与总量使用同一口径和容差；不必复制完整计算器，但不能只检查字段存在或同一错误值在多处重复。
- 新分支尚未实现上述相关检查时，如实记录缺失门禁；一次函数/API 定向核验可作为候选评估证据，不能冒充正式门禁已具备或自动发布已验收。

交付在已有记录中简写四点：**算了什么、假设什么、实际验证了什么、下一项未完成是什么**。区分“文件可恢复”“限定范围结果可用”“游戏机制已确认”，不强制每轮额外生成签收书或请求用户确认。

遇到已知实现错误，只阻断受影响范围。修复后按新的依赖指纹与新 run-id 交付；需要验证网页重算时只做一条直接相关成功路径。未请求的全仓回归、网页矩阵、旧案例成组运行仍不执行。

## 知识收尾（结果先交付，任务结束前完成）

本轮新增、修正或临时写进案例 profile 的可复用机制，完成实现后必须收尾：先查已有条目，复用或更新；没有则在 `knowledge/mechanisms/` 登记稳定 ID、当前参数绑定、规则/处理器与证据入口，并把通用规则从案例实例配置中分离。确属案例私有的输入可保留在案例中，但要写明不能共享的原因。

证据不完整可登记为 assumed/unresolved，尚未实现可登记 draft/not_implemented；不能把“没有全部实测”“没跑回归”或“先输出网页”当作不登记的理由。实现可复用与证据确认是两个独立维度，不得为入库伪造 validated 状态。

最小收尾只需：条目随正常加载可读、重建知识索引、本轮代表性稳定 ID 能命中。不要重跑导入、计算、网页或全套测试，不逐一巡查其它历史案例。

结果与网页可以先给用户；“先交付”不表示任务终止。最终说明本次工作完成前，应明确本轮机制是已复用、已更新、已新增，还是保留为案例私有并说明原因。仅保存 case profile、报告 JSON 或 mechanisms 链接，不等于已完成共享知识沉淀。

## 当前版本边界

- 现行计划/结果格式为 **plan-v4 / result-v6**；VC/FR/BH 三个 execution-v1 切片在限定范围内可用，Ballista 为 partial。能力与限制见 [current-status.md](current-status.md)。
- 支持范围不扩大为“任意技能/任意构筑可用”，也不是完整战斗模拟或完整回归通过。
- 历史计划/结果版本（v1–v3）仅作为兼容与历史边界保留，默认入口不应产生旧格式输出。
