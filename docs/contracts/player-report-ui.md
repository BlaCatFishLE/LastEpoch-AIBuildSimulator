# 跨 BD 玩家 HTML 与本地重算交付契约

**新存档 / 新 agent / 共享工程入口**：先读 §6「统一玩家报告质量基线与跨 agent 交付规范」（2026-11-12），再按需读取 §2 页面和 §3 重算约束。§6 包含用户认可的基线、实现入口、数据完整度、样式参数、交接流程与当前未验证边界。

## 网页验证的默认最小范围（用户要求）

- **只导入存档、更新数值或复用现有页面模板**：确认本次 HTML 已生成、链接指向当前案例即可；默认不打开浏览器，也不重新操作已验证的控件。
- **本次修改页面结构或样式**：最多打开一次默认页面，确认能够显示且没有明显阻断；不逐页巡查。
- **本次修改交互或重算服务**：只选一条直接相关的操作路径，看到一次成功结果即停止；已有观察足够时不重复核对其它页或同一结果的多个位置。
- 默认不做逐页/逐 Buff 检查、多场景数值对比、截图留档、多个分辨率或浏览器验证、配置保存/载入往返、下载/上传、连续请求/错误分支及旧案例对照。只有用户明确要求完整验证时才运行完整矩阵；用户只要求某一项时仅验证该项。
- “完整报告”“支持可勾选 Buff”“新增模型/机制知识”均是功能交付要求，不自动授权完整网页验收。功能应实际实现，验证范围默认仍按以上最小规则。
- 最小验证发现问题时，只修复该阻断并复查同一路径，不扩展成全面检查。先交付结果和链接；未做完整验证不作为扣留交付的理由，也不宣称已完成完整验证。
- 生成器已有的输入/结果绑定与完整性检查继续执行。页面最小检查不替代新增计算语义的定向检查；后者优先在函数/API 层完成，不扩展浏览器矩阵。本文及其它现行文档的完整网页验收矩阵均为按需参考，与本节冲突时以本节为准。


## 日常执行顺序（用户要求）

1. 先冻结、解析用户本次指定的存档，生成独立 BuildSpec 与 calculation-input。只检查当前输入和解码必需依赖；不要运行默认案例 doctor，也不要在导入前完整检查任何旧案例。
2. 导入后按当前构筑的技能、节点、被动、装备、神像、祝福及词条稳定 ID 查询沉淀知识，绑定当前实例的数值和点数。只按命中记录追溯必要证据；历史案例没有默认优先级。
3. 复用统一 DPS 流程的属性、乘区、暴击、目标、时间与报告组件。hit/DoT 仅表示击中与持续伤害的计算组件差异；技能行为由数据和规则表达，不能再按技能建立独立 DPS 模型。
4. 优先生成当前 BD 的结果和网页；区分研究/候选产物与可用于当前声明范围的计算结果。机制未知可以显式假设或缩小范围继续；已知来源、执行或账本错误不能用 partial 掩盖，也不能据此更新可用 canonical。
5. 复用已验证能力且未改变语义时，默认不追加测试阶段。新增或修改计算、绑定、条件、投影或门禁语义时，按受影响边界做少量正例/反例；既有同边界证据可复用，不按技能数或词条数铺测试。候选网页可先生成，相关最小检查在宣称该范围可用前完成；直接决定可计算性的检查可前置。细则见 `docs/workflow.md`“新机制接入与最小语义验证”。完整回归仍须用户单独明确要求。

所有历史案例地位相同，均为以前使用或建立流程留下的实例。案例名不决定默认输入、必读材料、知识检索顺序、回归基线或交付门槛。“走全套流程”不等于授权全仓测试。


日期：2026-11-07。状态：现行交付要求；已补入 Stage10 的来源/Buff 两页及全站游戏内名称要求。各项是否完成以对应 run 的验收为准，不能把本文当作实现完成记录。

适用范围：所有从正式流水线生成的玩家 HTML，包括 Black Hole、Flame Reave 和后续技能。目标是同样的视觉语言、操作入口和结果更新体验；技能内容按能力变化，不强行复制 BH 的点燃、冷却策略或目标条件。

依据：
- 作者本地的玩家版美化指南与历史验收记录（不随公开仓库分发）。这里只提炼跨技能要求；历史记录中的阶段分工与“不做重算”等范围说明不构成当前实施限制。
- 作者本地的 FR Stage7 / Stage10 UI 审查记录（不随公开仓库分发）。
- 流水线实施方案（作者本地实施记录，不随公开仓库分发）§6.5–6.6。

## 1. 现有能力与目标分开

BH 当前通过网页“计算 DPS”按钮调用本机 Python 服务，服务返回场景应用后的 HTML。它不是改动开关就自动重算，也不是浏览器内运行全部伤害公式。Stage7 的 FR 只有静态报告和生成场景 JSON 的控件；Stage10 已有计算与保存/载入按钮及本机请求代码。本次是静态 UI 审查，未重验完整服务链，不能沿用 Stage7 的“没有按钮”结论，也不能仅凭按钮存在宣布功能验收通过。

**V1 最低要求：每个已支持模型都能在同一套网页操作中修改目标/Buff，点击计算，在本机完成重算并看到一致的新结果；无需复制 JSON 或手动运行命令。** 自动重算可以作为统一增强，但不替代按钮、不降低正确性要求，不把“生成 JSON”或局部演示数值当成重算。

### 2.1 来源与 Buff 两页的统一基准（HTML-09～12）

UI 对照采用作者本地的历史报告页面作为结构与风格参照（页面为运行产物，不随公开仓库分发），不改变当前案例指针。具体字段示例与验收记录属于作者本地材料，不随公开仓库分发。

| ID | 必须满足的要求 |
|---|---|
| HTML-09 来源浏览器 | 复用 BH 的搜索/类别/状态筛选、来源分组及“来源/效果/状态”三列结构。同一来源多属性归组、必要时展开；不同实例不因同名合并。来源主名、所属位置/技能副行、属性数值与状态分层；总属性/武器原始明细不抢占首屏。当前模型的增伤来源与角色其它属性区分，相关性依据实际计算作用链判断。该相关性分组仅用于来源页，不得用于裁剪装备页的完整词条（见 §6.9）。 |
| HTML-10 Buff 卡片 | 复用顶部预设/保存/载入/重置 Buff、搜索/来源筛选、计算状态栏及结构化效果卡。卡片含游戏名、所属来源、一个当前状态、操作、分行效果值及必要条件；常驻只读效果不画假开关。目标状态集中在目标设置，命中数放技能设置；非伤害/不适用效果不占主要配置区。移除重复标题和技术应用表，效果对比按需展示。 |
| HTML-11 游戏名称与数值 | 全站来源显示使用同一解析器；`mod:`、contribution ID、字段路径、`[passive node ...]` 等不得进入玩家文本、展开详情、tooltip、无障碍名称或打印结果。显示实际装备/节点/技能/祝福名、可读槽位、属性和单位。依据 unit/operation 格式化百分比/点伤/层数/秒，区分加算与独立增伤；状态取实际应用结果，included 不等于 active，不能硬编码“生效”。 |

### 2.2 名称映射与显示数据边界

从当前案例的来源实例、BuildSpec/calculation-input、dataset/catalog、规则/effect 元数据和已有名称映射中解析游戏实体，再投影为玩家视图。解析优先使用稳定 ID/来源位置精确绑定，而不是用贡献 ID 截断、删前缀或替换下划线充当名称。

- 有可靠游戏中文名时采用中文；否则保留游戏英文专名，属性/操作文案统一。不得臆造译名。
- 物品主名为物品游戏名，槽位/词缀类别作副行；节点主名为节点名，所属技能/被动树及点数作副行。两个同名来源保留可读位置，不暴露内部实例键。
- 玩家视图应能表达 `source_name/source_subtitle`、`attribute_label`、原始 value/unit/operation、`formatted_value`、实际应用状态、条件短文案及内部来源引用。字段为设计要求，可适配现有结构，不要求为它们复制第二份规则或公式。
- 同一来源在来源页、乘区展开、攻速/冷却详情、Buff 卡、搜索结果及重算后的 HTML 中名称一致。未解析时使用可读类别/位置占位并在工程记录登记缺口；主伤害来源名称缺失阻止完整 UI 验收，不静默退回裸 ID，也不删除该来源掩盖问题。
- 原始 ID 保留在 JSON/ledger 和 DOM 绑定中；禁止玩家文本泄漏不等于禁止 HTML 字节中出现 ID。不要用对整份 HTML 的正则替换破坏数据、锚点或脚本。
- 数值按语义格式化，例如 percent=0.4 → +40%、flat=61 → +61；不得把所有小数当百分比，不能把加算值写成 more。状态不能只由 included 或开关值推定。
- 同一来源含常驻和条件增量时，未激活增量必须就地标明；来源组的汇总状态不能暗示所有属性均已生效。基线数值和实际贡献不因排版合并改变。

### 2.3 玩家文本的定义（裁定 1-C，2026-11-07）

**玩家文本 = 用户可见或可访问的全部内容**：主阅读区、抽屉、展开内容、tooltip/`title`、无障碍名称、打印输出，
以及运行时由 JS 渲染出的文本。仅对初始 HTML 做静态扫描，不能代表该定义下的验收通过。

- **允许（可读来源信息）**：游戏内实体名、槽位/所属技能、点数、可读属性名与带单位数值、实际生效状态，
  以及理解结果确有必要的简短范围说明。
- **禁止**：裸 `mod:`、contribution_id、字段路径、数据库字段名、内部节点序号；禁止把完整证据等级、版本、
  locator 和调试表翻译成中文后重新塞回抽屉。
- **机器绑定 ≠ 可见文本**：JSON、script 数据块、`data-*`、DOM id 可以保留原始 ID；一旦进入可见文本、
  `title`/tooltip、`aria-label` 或打印内容，就必须走玩家投影。两条既有规定（HTML-11 与 §2.2 的 DOM 绑定保留）不冲突。
- **参考物不豁免**：BH 现有来源抽屉渲染"证据与版本"和数据库字段的行为同样违规；P3R 需把 BH 抽屉与 FR
  主区/抽屉一起修正，不能以"BH 也这样"为由放过。
- **验收覆盖**：点击后生成的内容、tooltip、无障碍名称与打印文本；不得用对整份 HTML 的正则替换来消除 ID。

## 3. 本地重算（LIVE 系列）

| ID | 必须满足的要求 |
|---|---|
| LIVE-01 双使用模式 | 双击单文件可离线查看全部已生成结果，无外部资源、无页面加载自动请求。**合法单文件（file://，含 bindings/meta 与真实本机端点）也应支持显式点击计算时才请求本机引擎**；服务未启动只在尝试计算时给简短提示，不在页面加载时主动探活/写提示。启动命令放使用说明，不占玩家页面。不得以“file 页面必然不能访问回环服务”为由强制禁用重算（如需服务页独占必须改契约并重新验收）。 |
| LIVE-02 模型路由 | `le.ps1 serve --case ...` 必须按案例的模型/技能能力选择适配器，绑定本案例的快照、规则、场景和端口。FR 不进入 BH ruleset loader/registry；未知模型明确不支持，不静默使用默认 BH。公开命令相同不等于功能已经共享。 |
| LIVE-03 唯一计算实现 | 网页与 CLI 调用同一 Python 领域计算入口和规范化场景。前端只做输入、格式化与呈现，不另写伤害公式、命中权重或技能政策。控件、默认值、上下限与支持状态由模型能力描述提供，不在 JS 硬编码案例效果。 |
| LIVE-04 场景绑定 | 请求/响应带 case/model、输入与规则指纹、场景指纹或 revision、request_id、report_ref；加载保存配置时先按 `le-report-config-v1`（`tools/phase3/schemas/le-report-config-v1.json`；Python `recalc.validate_report_config`；页面 JS 同一 schema/错误码/顺序，共享样例见 `le-report-config-v1.examples.json`）验证格式、case/model 绑定、输入/规则指纹、能力版本、report_ref 与完整场景，全部通过后才原子应用控件；无 binding 旧文件返回明确 legacy 结论（`legacy=true` + 错误码 `legacy_config_no_binding`，拒绝自动应用），不静默视为有效绑定。错误案例、过期规则、未支持字段或非法层数明确拒绝/标不可用，不静默忽略或解释成 0。 |
| LIVE-05 修改与应用分开 | 控件改变后显示“设置已更改”，已显示结果仍属于上次成功场景。点击后显示“计算中”；只有成功且绑定匹配的响应才改为已应用。失败保留编辑值与上次成功结果，提示重试；不要先把开关标为已生效。 |
| LIVE-06 一致更新 | 一次成功重算同时更新 KPI、分项、公式当前值、来源生效状态、命中/频率/时间数据、目标摘要及导出结果；当前页签、配置和支持的窗口选择保留。不能只换首页 DPS，其它页仍是旧结果。 |
| LIVE-07 防止旧响应覆盖 | 每页加载生成独立 `client_session_id`，请求/响应回显；服务端按 `(report run_id, client_session_id)` 隔离 accepted revision，同一 session 内 `client_edit_revision` 严格递增、旧/重复 revision 明确拒绝（`stale_edit_revision`），不同标签页/刷新互不干扰。计算期间继续编辑、载入配置、切换预设/目标或模型时，使旧请求失效；快速连续请求按绑定与序号接纳最新有效响应；响应绑定/会话不匹配、accepted_revision 不前进或 request 已过期时丢弃并保留旧结果。重置和载入配置也进入同一个修改状态流程。旧客户端无 session 时服务端按隔离 request_id 作用域兼容并在响应标记 `client_session_legacy=true`。 |
| LIVE-08 配置与结果 | 保存配置为 `le-report-config-v1`：`{schema_version, binding, scenario}`，`scenario` 是完整规范化编辑场景（含 preset/baseline_profile、states、hit_override/target 等），`binding` 与页面 bindings 一致；载入先校验再原子应用，控件可往返，尚未重算时不宣称已应用；校验失败/legacy 无绑定不修改旧配置且明确提示。保存结果对应最后一次成功计算；不能把未应用控件打包成该结果的计算条件。默认配置/当前配置比较须同口径，不把 legacy_single_skill 与 build_base 的差额标为 Buff 增益。 |

控件与新能力的最低契约（同样适用于未知机制的假设输入）：

- 当前来源身份/已分配点数等冻结事实只读；编辑构筑应走重新绑定路径。场景控件只暴露运行时实际消费的值，不能让 UI 修改被编译常量覆盖的字段。
- 合法范围、类型、零值语义与后端一致。允许 0 时有对应无事件/无增量结果；不支持则在能力描述与输入校验明确限制。未实现的控件不可伪装为可用。
- 显式假设可作为可编辑参数；数值受钳制或条件不适用时允许不变，但要按真实应用状态解释，不能假装已产生增益。
- 候选/限定范围/已知错误在相关结果处简洁表达，不把所有研究问题堆成玩家警告墙。研究 HTML 不伪装为 DPS 报告。

上述语义按 `docs/workflow.md`“新机制接入与最小语义验证”在 API/函数层选择必要检查；页面复用仍不默认开浏览器，交互修改仍只验证一条直接相关成功路径。

服务保持仅本机回环与冻结输入约定。交互计算默认不覆盖磁盘报告；需要保存正式结果时使用新的 run，并遵守流水线提交与历史不可变约定。

V1 可先复用 BH 的返回整份 HTML 方式，前提是新 HTML 也由共享页面生成器输出、保留配置和视图状态。局部更新/固定网页 + 结构化响应可后续演进，不以接口升级为借口延后 FR 的可用重算。

## 4. 实现边界与复用位置

当前可复用入口是 `tools/phase3/src/le_calc/report_ui/`（shell、pages、labels、sources、assets）和 `tools/phase3/src/le_calc/serve.py`。这些实现仍含 BH 专有语义，需要适配，不能把 Hit 结果直接塞进 BH schema。

拟实施分层：
1. 模型适配器：将现有 BH/Hit result 投影为统一玩家视图，声明可用页面、模式、目标字段、Buff 控件、可读来源和重算能力；原始 result schema 与 ledger 保持兼容。
2. 共享页面：统一 shell、表单、来源组件、状态与保存/载入交互；模型专页使用相同组件。不再按技能另写整套 header/footer、文案、JS 和条件表单。
3. 服务适配器：同一 `serve --case` 加载模型计算入口，与 CLI 共用场景校验和计算，输出共享视图/HTML。
4. 报告缓存：纳入视图适配器、共享模板、CSS/JS、标签与能力描述的指纹。只改 UI 时复用数值并重建 HTML；计算缓存命中不能使旧页面永久保留。

**P3R 落地（2026-11-08，已实现）**：

- 元数据以伴随文件 `report-capabilities.json`（`report-capabilities-v1`）承载：`ui_contract_version`（当前值 `le-player-report-ui-v1`）、
  `renderer_fingerprint`（**单一来源（O-C）**：`le_calc.report_fingerprint.renderer_fingerprint()`；`report_capabilities` 与 `report_ui.document` fallback 均委托它，HTML meta、bindings、artifact、缓存键同值，覆盖 `report_ui/**` 全部文件及 `app.js`/`shell.js`/`recalc_contract.js`/assets 与模型渲染器）、
  `capabilities`（pages/target_fields/buff_controls/windows/modes/baseline_profiles/profile_states；`recalculation` 含 `session_scoped_revisions`/`client_session`/`report_config_schema`）、`acceptance_refs`（HTML-01～12/LIVE-01～08 与案例 expected 的仓库相对引用）、`cache`（numeric_key/report_key/端点/指纹）。
- 页面内嵌 `<script id="le-recalc-bindings" type="application/json">`（`le-recalc-bindings-v1`：case_id/model_id/capabilities_version/ui_contract_version/renderer_fingerprint/report_ref/input_fingerprints/recompute_endpoint）；
  页面客户端据此构造 `le-recalc-request-v1`（`request_id`、`client_session_id`、`client_edit_revision`、`scenario`、`command`），响应在应用前校验全部绑定 + `client_session_id` + `accepted_revision` 次序（LIVE-04/07）。
- **配置契约（R3）**：`le-report-config-v1` 保存当前完整场景 + binding；载入用共享校验（Python `recalc.validate_report_config` / 页面 JS），错误码/顺序见 `tools/phase3/schemas/le-report-config-v1.examples.json`；无 binding 历史格式返回 legacy 结论并拒绝自动应用（`legacy_config_no_binding`）。
- **会话序号（R8）**：请求可选 `client_session_id`（每次页面加载生成）；服务端按报告 run + session 隔离 `accepted_revision`，跨标签页/刷新互不干扰；无 session 旧客户端使用隔离 request_id 作用域并在响应标记 `client_session_legacy=true`；响应头 `X-Client-Session-Id`/`X-Client-Session-Legacy`。
- 服务端契约模块 `le_calc/recalc.py`；`serve --report` 显式选择报告并校验端口一致；报告缓存键含端点/UI/渲染指纹/result digest，数值缓存键不含端口（3-A）。
- 历史 run（无 `report-capabilities.json`）仍可被默认选择并给出警告；完整行为见作者本地 P3R 报告（不随公开仓库分发）。

## 5. 用户明确要求完整网页验证时采用的矩阵

以下矩阵不在日常导入/报告交付中默认执行，也不要求每次功能修改全部重跑。未被用户明确请求的验证项按本文开头的默认最小范围处理。

| 用例 | 通过条件 |
|---|---|
| 当前任务的默认结果 | 当前构筑各计算组件走相同骨架；读取本文 HTML-01～12 逐项验证，专有页按能力启用；角色、来源与状态来自各自输入。 |
| 两页对齐 | 增伤来源和 Buff 设置按 HTML-09/10/12 与指定 BH 参照做同尺寸结构及截图对照；搜索/筛选/明细/工具栏与同名操作语义一致；不照搬 BH 专有数据或诊断预设。 |
| 名称/单位/应用状态 | 全站玩家文本（含展开/提示/无障碍名称/打印）零原始来源 ID；支持来源均可映射到游戏实体；原始 JSON 保持完整。覆盖 percent/flat/层数/时间及 included=true、active=false 的真实用例，默认/重算后结果均检查。 |
| 离线打开 | 不请求外链/本机服务；导航、浏览、配置操作可用；点击计算时连接失败有短提示，旧结果和编辑值不丢。 |
| 本地目标/Buff 重算 | 针对当前任务更改至少一个会影响伤害的目标条件及一个支持的 Buff/层数，响应绑定正确；与相同输入/场景的 CLI 数值、分项、来源状态在项目容差内相等。选择实际会影响该模型的条件，不能只断言“某个数变了”。 |
| 页面完整更新 | 初始与应用后的所有适用页、目标面板、导出结果一致；保存→载入→计算能往返；重置目标与重置 Buff 职责明确。 |
| 不支持与错误 | 不支持机制不可伪装成可用开关；非法输入、错误 case、过期指纹、服务失败均不能更新为成功结果。未支持伤害范围继续在数据与短范围标签保留。 |
| 连续操作 | 连续计算、在途修改、载入/重置不被旧响应覆盖；失败重试不丢配置。 |
| 视觉与操作 | 1440/1080/720px 检查所有适用页、目标面板和重算后状态，留截图/尺寸/输入/结果引用；检查焦点、长名称、单数值与表格溢出。未实际渲染时只能写静态审查，不能声称视觉通过。 |
| 新 BD 复用 | 换装备/点数仍使用同一页面和服务通道；无旧案例的控件、名称、参数或场景残留；共享模板变动使报告缓存失效。 |

静态规则检查只针对渲染给玩家的文本与控件，不禁止内嵌 JSON 出现工程字段，也不把整个 HTML 中存在 `fetch` 视为违反离线要求。加载无请求与用户点击后向本机重算是两个测试阶段。

Stage7 审查时，FR 的 `test_html_pages_and_status_banner` 固定旧文案和横幅，`test_html_is_self_contained_offline` 禁止整个 HTML 出现 `fetch(`；后续实现需按本契约核对这些测试，不能把该历史观察作为当前测试未改的断言。保留结果/来源/数值验证，增加真实跨模型服务与页面交互测试；不能仅换成新的字符串存在断言。

交付与验证范围分别记录：实现存在已知功能缺口时如实说明，不把未实现功能写成已完成；仅未执行完整网页验收，不构成交付阻断。默认完成最小验证即可交付报告，不必先遍历数值/HTML/LIVE 全部矩阵；未做的验证不宣称通过。历史报告不回写。

## 6. 统一玩家报告质量基线与跨 agent 交付规范（2026-11-12）

本节是新存档、换技能、换 agent、换机器时的现行 HTML 输出要求，不是某个技能的美化方案。本文开头的默认最小验证范围继续有效；下面的内容要求不自动扩大验证范围。

### 6.1 质量基线、适用范围与优先级

用户在 2026-11-12 明确认可的统一报告为作者本地运行产物（`reports/<case>/<run-id>/` 下的 `dps-report.html`；不随公开仓库分发）。新报告按同一质量基线生成，不复用其历史数值。

该页面是信息组织、视觉层级和可读性的基线。它取代 §2.1 中旧 BH 页面作为**后续统一报告的首选外观参照**；旧页面仍可用于查找曾提供的信息，不再决定新报告的数据或计算口径。基线文件不存在时，按本节与共享源码复现，不要求接收方找到历史报告才能生成新报告。

- 继承：结果先行、浅色卡片、清晰乘区、实际来源、时间与循环、完整装备词条、可用的场景控件。
- 不继承：Black Hole 名称、角色、装备、数值、怪物条件、双充能、Ignite、固定窗口、策略 ID、存档路径、端口或 run-id。
- 新增技能复用同一计算流程与展示组件；可以新增通用数据能力，禁止用 `case_id`、技能名或存档名判断整套页面模板。
- 不得退化为 JSON 字段表、应用账本、覆盖统计或一张 DPS 汇总表。工程信息保留在结果、账本与导出文件，玩家页面呈现它们对应的游戏含义。
- 本节规定的是输出质量，不保证尚未支持的机制已经可算。能力缺失要明确记录，不能靠仿照参照页面填值。

### 6.2 唯一实现入口与职责

以下均为仓库根相对路径。接手 agent 修改 HTML 或排查内容缺失时，先沿此链定位，不另建一次性 HTML 生成脚本作为正式交付入口。

| 层 | 当前入口 | 职责与约束 |
|---|---|---|
| 正式运行 | `scripts/le.ps1` | 导入/准备/运行/服务统一入口；当前案例决定输入，新 run 承载输出 |
| 报告阶段 | `tools/phase3/src/le_calc/workflow/unified.py` 的 `render_stage` | 读取当前 plan/result，保留已有完整计算与装备明细；BuildSpec 仅补真正缺失的展示字段，不以局部摘要覆盖完整明细；写 HTML 与伴随文件 |
| 统一报告路由 | `tools/phase3/src/le_calc/dps_report.py` → `tools/phase3/src/le_calc/plan_v4.py` 的 `render_report_v6` | 将 result-v6 交给统一玩家展示层；不得接回旧技能页面脚本 |
| 玩家展示层 | `tools/phase3/src/le_calc/report_ui/unified_report.py` | 数据投影、信息组织、页面组装；不得重新执行伤害公式 |
| 共享骨架与组件 | `tools/phase3/src/le_calc/report_ui/document.py`、`components.py`、`shared_ui.py` | 页头、导航、KPI、表格、来源分组、效果卡、导出与抽屉统一复用 |
| 样式与交互 | `tools/phase3/src/le_calc/report_ui/assets/style.css`、`dps.css`、`unified.css`、`shell.js`、`unified.js` | 保持外观与操作一致；离线加载无网络请求；显式计算使用本机引擎 |
| 缓存与绑定 | `tools/phase3/src/le_calc/report_fingerprint.py`、`recalc.py` | 模板/资源变化使报告缓存失效；保持当前输入、规则、场景与结果绑定 |

当前 `plan_v4.py` 的结果转换通过 `report_details` 保留引擎已经生成的详细结果。`report_details` 是现有兼容承载，不能把它误解成新的伤害模型，也不能把其中的历史字段名当作未来技能必须使用的业务概念。

修改共享展示层后，首次生成与本机重算必须走同一个渲染入口；不能只让 CLI 输出漂亮，而重算又回到旧版页面。

### 6.3 页面信息架构（UR-01～06）

默认导航顺序为“总览 → 伤害构成 → 时间与循环 → 增伤来源 → 装备与神像 → Buff 设置”。目标条件集中在唯一的“目标设置”入口，打印与结果导出集中在“更多”。模块按真实数据启用；整页无适用内容时可以省略该页，不增加空壳页。

| 要求 | 必须展示的信息 | 数据不存在时 |
|---|---|---|
| UR-01 总览 | 主策略预计 DPS、明确的观察窗口、单次施放伤害（有数据时）、窗口总伤害、实际施放次数/并发（适用时）；关键动作/冷却/持续时间；目标摘要；同口径伤害构成与窗口 DPS 图 | 未计算项显示“未提供”或省略，不显示为 0；不把单次命中伤害放入 DPS 卡 |
| UR-02 伤害构成 | 每个实际伤害组件的类型、结算范围、基础与附加、加算、独立增伤、适用的暴击和目标倍率、当前最终值；可展开查看各乘区真实来源 | 已计算但丢失明细属于投影缺口，先修复传递；未计算的乘区不能由 HTML 猜测 |
| UR-03 时间与循环 | 各实际策略的可读名称、各观察窗口的伤害/DPS/次数/尾伤；有真实施放记录时展示时间分布和逐次记录；有真实批次数据时可展示施加、到期和层数 | 只有窗口汇总时只画窗口图；不得插值冒充逐时 DPS、层数或事件曲线 |
| UR-04 增伤来源 | 搜索、类别/状态筛选，“来源/效果/状态”三列；同一来源实例多属性归组；来源主名与槽位/所属技能副行；按实际作用组件解释状态 | 不因缺少可读名改为显示内部 ID；补名称映射，未解析状态保留在工程结果中 |
| UR-05 装备与神像 | 当前装备、神像、祝福的实例名称、槽位、基底和完整可读词条；包括与主技能无关、防御、功能和未参与计算的属性；保留真实数值、单位和已知阶级，执行 §6.9 | 只有词条名称而缺少 roll 值时不伪造数值；不把原始编码当 roll；明确缺失，不宣称完整 |
| UR-06 Buff 设置 | 当前引擎实际支持的开关/层数、上下限、效果、适用条件和只读状态；保存、载入、重置与明确的计算状态；目标条件进入目标设置 | 没有支持的控制定义就不造控件；静态条件不冒充可操作 Buff；缺失交互如实说明 |

伤害构成必须按能力选择内容：

- 命中：基础/附加效用、加算、独立、暴击期望、目标结算；有多命中时展示次数及权重，有频率时展示动作/冷却约束。
- 本体持续伤害：逐跳基础、跳数/间隔、持续时间、加算/独立/目标结算及总伤害。跳数和时间是计数/时间量，不装饰成“增伤乘区”。
- 异常或其它施加效果：单层伤害、持续时间、施加频率、每次期望层数/总层数、实际来源；期望层数不能标成实测整数层。
- 充能或并发：最大充能、恢复、动作时长、施放时刻、最大并发和策略差异。无此能力的技能不出现这些控件或空表。
- 公式只展示当前组件实际使用的一条主链。每项与当前来源明细对应，不复制基线公式，也不在浏览器另算一套结果。

### 6.4 数据保真与可移植契约（UR-07～12）

**UR-07 明细不能在转换中丢失。** 引擎已经计算的信息必须传至统一结果/玩家视图，不能只留下最终伤害。当前主要映射如下；这是现有数据入口说明，不是强制新技能模仿历史字段名。

| 信息 | 当前入口 | 使用规则 |
|---|---|---|
| 主策略与窗口 | `totals`、`evaluations`、`policy_results`、`windows` | 显示主策略对应值；窗口、单位和策略不能混用 |
| 组件乘区 | `report_details.components`，兼容 `components` | 优先完整计算明细；不得把计划中的占位默认值当成已结算倍率 |
| 单次结果 | `report_details.single_cast` | 单次总伤害可含尾伤，必须与窗口截断伤害区分 |
| 调度与时间 | `report_details.loops`、`cast`、`cooldown`，或原生策略记录 | 时间图只取真实记录；别的频率驱动可提供等价通用投影 |
| 施加结果 | 当前兼容字段 `report_details.ignite`、`ailments` 与施加单元 | 历史名只在适配边界使用；新异常按施加能力扩展统一组件，不能创建技能专页 |
| 来源及生效关系 | `contributions`、`contribution_application_summary`、`applications_ledger` | stable ID 用于关联；玩家文字用实体名。没有实际应用记录不能只凭 `included` 宣称“生效” |
| 装备 | `report_details.equipment[].mods`，补充来源为当前绑定的 BuildSpec 装备 | 保留当前实例全部已解码词条，不按主技能相关性或计算支持状态过滤；禁止用 BuildSpec affixes 或贡献清单覆盖完整 mods，详见 §6.9 |
| 可编辑条件 | `report_details.controls` 或统一能力定义，加当前 `scenario` | 定义决定支持范围，场景决定当前值；重置默认值应有明确来源，不能无说明地变成最后一次重算值 |

**UR-08 数值语义先于字段名。** 同一张图、占比、对比表的分项必须属于同一策略、同一时间范围和同一结算口径。历史兼容键 `hit_damage` 不足以证明它是命中伤害；必须核对实际组件类型。不得把单次本体与 120 秒异常总量相加或比较。缺失、未计算、明确为零必须区分；未知值不能用 `or 0` 掩盖。

**UR-09 名称与单位可复用。** 使用稳定来源身份匹配装备/被动/节点/技能/祝福名称。同名的两个戒指或神像不能合并；已计入、条件未满足、不适用、未解析和重复抑制不能统称“排除”。百分数按真实 unit/operation 转换，`0.55` 的百分比值显示为 `55%`；`×1.55` 是倍率，不再显示为 `155% increased`。长名称允许换行，不能截断到无法识别。语言映射缺失时保留可靠英文游戏名，不编造中文名。

**UR-10 结果与明细一起更新。** 重算后的 KPI、乘区、来源状态、装备投影、时间记录和导出数据应指向同一结果。更改控件只改变编辑状态；绑定校验失败、服务失败或过期响应不得覆写上次成功结果。单文件可离线阅读；“可离线阅读”不等于“脱离引擎重算”。配置文件绑定不匹配时必须拒绝，不能为换机器或换存档而绕过校验。

**UR-11 数据不足的处理顺序。** 先判断数据是“未计算”还是“转换丢失”：后者补通用传递链；前者按实际能力显示范围、登记缺口。缺少一种能力只影响对应模块，不削减已有数据的其它模块。仅有汇总值时可以交付注明范围的报告，但不能称其已经达到本基线的信息完整度。

**UR-12 无隐藏机器依赖。** 名称、词条、规则与默认场景从当前案例及其依赖获取，不从前一个对话、浏览器缓存或某个人的绝对路径获取。HTML 内嵌所需 CSS/JS/图表数据，不依赖 CDN、外部字体或报告目录旁的临时资源。本机重算端点属于当前绑定，由正式入口生成；不能硬编码另一台机器的地址。代码、契约和数据依赖需要一并随工程交付，仅发送一个旧 HTML 不能赋予对方生成新存档报告的能力。

### 6.6 接手、新存档与共享操作规程

1. **接手先读本节与 §2/§3。** 确认本次案例、主技能和输入，保留仓库现有改动。用户仅要求文档或样式时，不重导入存档、不重算历史案例。
2. **新存档按正式导入流程建立新案例。** 绑定新 BuildSpec/输入/场景，匹配当前来源知识。不要复制基线数值、expected、装备清单或 Buff 状态。
3. **按当前能力列出页面所需数据。** 有组件乘区就传乘区，有施加批次就传批次，有调度记录就传时间。先核对转换是否丢字段，再判断是否需要新增计算能力。装备按 §6.9 建立当前实例词条清单并逐条核对，不以增伤来源清单代替。
4. **复用统一展示入口。** 只能给共享组件增加通用字段/布局；新技能特殊机制以能力/元数据表达。临时本地手改 HTML 不算正式实现。
5. **在新 run 中生成报告。** 保留流水线的输入、绑定与结果完整性门禁；模板变化应失效报告缓存。历史 run 不覆盖，交付链接明确指向本次案例和 run。
6. **按本文件开头执行最小验证。** 模板复用只确认产物和链接；结构/样式修改最多打开一次默认页；交互修改只验证一条直接相关路径。未要求时不运行全仓回归、多分辨率或旧案例巡查。
7. **交付说明区分三件事。** 当前报告包含什么、当前机制范围缺什么、本轮实际验证了什么。文档要求、代码存在、单案例实测和跨技能验证不能互相替代。
8. **共享工程时保留可再生成条件。** 至少保留 `AGENTS.md`、本契约、正式脚本、共享报告源码/资源、当前案例及其引用的输入/规则/知识/数据依赖。按项目既有打包规范处理外部数据。路径使用仓库相对引用；端口变化或依赖变化通过新报告重新绑定。禁止为了便携直接修改历史绑定/哈希。

其他 agent 可直接使用以下交接要求（占位符必须替换为本次实际案例）：

> 为 `<当前案例>` 生成玩家 HTML。先读 `AGENTS.md` 与 `docs/contracts/player-report-ui.md`，以 §6 的统一报告基线为准；走正式流水线与共享展示层，按当前数据能力呈现。保留已计算的乘区、来源、时间与完整装备词条；装备执行 §6.9，含与主技能无关的防御/功能属性和未参与计算的效果，不按相关性裁剪，不以 BuildSpec 摘要覆盖完整解码明细。不复制基线存档的数据，不把工程账本铺进页面，不在 HTML 重算伤害。新 run 输出，不覆盖历史。缺失数据先查转换丢失，再标记真实未支持范围。验证遵循默认最小范围，交付本次报告链接并准确说明实际验证范围。

### 6.7 当前已知边界与后续禁止倒退项

以下区分“要求”和“已有证据”，避免新 agent 因看到本规范就认定跨技能全量验收已完成：

- **已有证据**：上述基线由正式流水线生成，结果校验通过，用户认可页面效果；原有两项未确认属性仍保留。此前 agent 的浏览器操作被 Computer Use 检查中止，因此没有 agent 完成网页重算验证的结论。
- **现有实现边界**：当前兼容明细仍含 `ignite`、`single_cast` 等历史结构；统一 renderer 的施加效果展示目前主要消费 `ignite`，不能据此宣称任意异常均已接入。其它异常接入时，应扩展通用施加效果投影，不复制一套页面。
- **尚需按新案例核实**：纯命中字段映射、不同目标字段/可编辑范围、所有条件的可读名称、原生 v6 明细、重置默认值语义及非充能策略图等。当前实现中的默认字段、标签兜底和固定页面清单不是新案例的业务依据；与本节不符时是待修实现，不是规范豁免。
- **不等价要求**：每个案例需要相同的可读性、完整性和操作语义；不要求每个案例有完全相同的六页、相同的四个 KPI 或黑洞专有图表。
- **禁止倒退**：不得以“统一模型只能提供通用表格”为由丢明细；不得以“字段不存在”为由把未算项显示成 0；不得仅用静态示例图装饰缺失的时间数据；不得为了通过旧字符串测试恢复原始 ID 或工程字段页面。

本轮仅补充报告交付规范，未新增或修正伤害机制；继续复用既有机制知识，无需为文档变更新增机制条目。

### 6.8 跨技能 Buff 完整性（UR-14，2026-11-12 补充）

主技能不是来源筛选边界。每次导入必须检索当前构筑**全部专精树、职业被动、装备、神像与祝福**中可能作用于主技能的效果。主技能模板只列了自身节点，不能据此宣称 Buff 页完整；页面存在三个开关也不代表来源接入完整。

- 建立“当前来源 → 命中机制 → 参数绑定 → 条件定义 → 计算作用域 → 控件/只读说明”的可追溯关系。已支持、未启用、不适用、未实现和来源缺席分别处理；未知效果登记缺口，不能无声消失。
- Craterborn 等临时效果按固定条件估算，说明维持状态的假设，不隐含模拟前置技能的施放成本。常量与每点值分开：当前点数用于 per_point，noScaling 常量不能再次乘点数。
- Preparation 等“下一次施法”效果必须注明 `single_cast_only`：可提升独立单次施放结果，但没有消费/刷新动作模拟时不得提高持续循环 DPS。单次与循环的来源状态、乘区口径应解释清楚。
- 复合条件必须完整表达。例如 Chilled Touch 需要效果激活且目标冰缓；Frozen Steel 的冰缓或冻结是任一条件，同一效果不能因两条件同时满足而翻倍。
- 新存档缺少对应来源时不生成该 Buff；存在来源但机制未实现时，保留可读的范围说明/研究记录，不能伪造有效开关。不要把历史存档的全部卡片无条件复制到当前存档。
- 当前共享规则入口为 `tools/phase3/rules/shared-conditional-node-buffs-v1.json`，绑定器为 `tools/phase3/src/le_calc/conditional_node_buffs.py`；规则路径必须进入依赖指纹。当前已接入 charge_dot 执行链；其它驱动需完成接线和对应定向验证后才能宣称支持。
- 核对这条关系属于输入/结果完整性工作，不要求逐个点击全部 Buff。修复计算绑定时，仅做能证明实际点数、作用组件与单次/循环边界的必要定向检查；网页仍按最小验证规则。


### 6.9 装备全量展示与交接核对（UR-15，2026-11-13 补充）

**装备页展示当前物品本身，不能只展示对主技能 DPS 有贡献的部分。** 本节适用于全部装备、神像与祝福，以及新存档、换主技能、换 agent、首次生成、本机重算和导出结果。增伤来源页的相关性分组、伤害引擎的支持范围均不能改变装备清单的完整性。

#### 展示范围与缺失处理

- 必须保留当前实例的全部玩家可读属性：基底固有/隐式、显式前后缀、封印、暗金固有效果、传奇合成附加词条，以及神像与祝福属性；按当前数据实际存在的通道展示，不凭历史案例补造。
- 生命、护甲、抗性、闪避、移动、资源、回复、其它技能等级/效果等，即使与主技能无关或不提高当前 DPS，也必须展示。效果未启用、条件不满足、尚未接入计算、机制未确认，均不是删除物品词条的理由；展示不表示该效果已计入 DPS。
- 默认提供完整词条，不能默认只显示“与主技能相关”。可按通道分组或折叠长列表，但必须能够读取全部内容，打印也应保留全部词条；不能截断、只取前几条，或只放进内嵌 JSON 而玩家无法查看。
- 显示当前实例的真实数值、单位、条件和已知阶级。缺少 roll、名称或效果文本时保留该条目及可读缺失说明，工程记录保留原始身份和缺口；不填 0、不猜值、不用编码作数值，也不静默丢弃。可靠英文游戏名可保留。
- 仅内部实现标记、序列化辅助记录、经确认的重复解码记录可不单独显示；须在工程映射记录逐条写明原因。游戏效果的“不适用/未支持/无 DPS 贡献”不属于隐藏理由。多个底层 mod 组成同一条游戏词条时，可以合成一行，但所有底层记录必须可追溯，效果及数值不能丢失。

#### 数据来源与合并规则

- 以当前输入绑定下的完整解码物品明细为清单依据；当前 `report_details.equipment[].mods` 已有完整数据时必须保留。BuildSpec、`binding.equipment`、`affixes` 或贡献账本可能只是摘要，不得替换完整清单，也不得反向决定哪些词条值得展示。
- 名称、槽位、基底等缺失元数据可从同一当前实例补齐。不同来源出现数值冲突时核对快照、解码通道和单位，并记录未解决差异；不得静默选取较短摘要或拼成重复词条。已有完整明细缺失时先修投影传递，不能称为“引擎不支持”。
- 关联键至少能区分物品实例、词条通道和具体词条记录；只有属性 ID 不足以唯一标识重复词条。没有稳定实例 ID 时，使用当前快照内可追溯的槽位/位置与记录索引。不能按名称、属性名或相同数值合并两个戒指、神像或不同通道的真实属性。
- 装备属性与计算贡献是不同口径。例如物品的原始词条值与机制换算后的最终贡献可能不同；装备页保留物品原值，来源页说明适用的换算，不用计算后的合计替换原始词条。

#### 最小完整性核对与交付判定

1. 从当前绑定的完整解码数据建立“物品实例 → 全部词条记录”的预期清单；不能从已筛选的 HTML/贡献清单反推预期清单。
2. 对照预期清单、传入渲染器的数据、HTML 可读取的装备内容及内嵌/导出数据，逐条核对身份、效果、数值和单位。格式化允许四舍五入，但底层数据保留精度；合并展示必须保留记录到展示行的对应关系。
3. 每条记录必须对应已展示的词条、可读的缺失占位，或有依据的不展示原因。缺失占位表示已记录缺口，不等于词条完整。只核对装备件数、总行数、关键词存在或总 DPS 相等均不足以判定通过；同样数量也可能缺项、重复或替换。
4. 此核对作为共享报告生成链的完整性要求，首次生成与重算使用同一规则；不要求逐卡浏览器巡查或全仓回归。发现投影删项应修复共享链，历史 run 不回写；数据确实不足时可交付注明范围的报告，但不得宣称“装备词条完整”或 UR-15 通过。
5. 自动门禁必须实际实现并验证后才能宣称能自动拦截；文档条款、旧 PASS 或一次人工核对不构成自动保证。尚未实现门禁时交接必须明确记录，并按上述清单进行当前产物的静态核对，不能将未检查标为通过。

本节针对的已知退化（完整 mods 被局部 affixes 摘要覆盖）来自作者本地迁移审计记录（不随公开仓库分发）：装备实例数量不变仍可能遗漏大量词条。本次补充的是规范与验收口径，**没有因此修复生成器、补齐历史 HTML 或实现自动门禁**；不新增伤害机制，复用既有机制知识。
